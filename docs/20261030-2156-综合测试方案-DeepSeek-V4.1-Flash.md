# 《一刀999》综合测试方案（0.8.5）

- 时间：2026-10-30 21:56（Asia/Shanghai）
- 版本：0.8.5（本轮只新增测试方案，不改游戏代码与数值）
- 范围：难度数据补齐 → 修正案 A/B → 全量回归 → 部署验收，一条可执行链路
- 状态：规划文档，执行时按阶段产出数据并回填到对应技术记录

## 一、测试目标

1. **补齐缺失的难度证据**：道士第 30 / 75 关，三职业第 60 / 90 关，并用同一版探针重测所有旧数据。
2. **验证或否决修正案**：第 75 关是否拉长 `specialInterval`、第 30 关法师是否回调 `attackMult`、第 60 / 90 关零死亡是否上调。
3. **守住功能与性能底线**：每次提交跑静态检查、单测、UI 回归；发布前跑百图 e2e 与 perf。
4. **部署可验收**：Instabox 沙箱上的公网地址、资源加载、真浏览器进战斗、隧道失效恢复。

**非目标**：移动端真机触控、多人服务器、经济深度建模、安全渗透；这些仍留在【下一步待实现】。

## 四、阶段 A：难度数据补齐（P0）

### 4.1 执行矩阵

每格 `ONEKNIFE_PROBE_RUNS=8`、`ONEKNIFE_PROBE_SEED=2000`（第 n 次运行用 seed+n-1），
单次命令覆盖两关：

| 优先级 | 职业 | 关卡 | 命令 | 说明 |
|---|---|---|---|---|
| P0 | 道士 | 30, 75 | `ONEKNIFE_PROBE_CLASS=taoist ONEKNIFE_PROBE_STAGES=30,75 ...` | 唯一没测第 75 关的职业 |
| P1 | 法师 | 60, 90 | `ONEKNIFE_PROBE_CLASS=mage ONEKNIFE_PROBE_STAGES=60,90 ...` | 验证「零死亡」是否职业特定 |
| P1 | 道士 | 60, 90 | `ONEKNIFE_PROBE_CLASS=taoist ONEKNIFE_PROBE_STAGES=60,90 ...` | 同上 |
| P1 | 战士 | 60, 90 | `ONEKNIFE_PROBE_CLASS=warrior ONEKNIFE_PROBE_STAGES=60,90 ...` | 旧探针数据需刷新 |
| P2 | 法师 | 30 | `ONEKNIFE_PROBE_CLASS=mage ONEKNIFE_PROBE_STAGES=30 ...` | 已有 0.8.2 数据，仅在要改 0.88 时重测 |

前置：`npm install`、`npx playwright install chromium`、`npx playwright install-deps chromium`、
`ONEKNIFE_CHANNEL=chromium`、`npm run serve`（4174 端口）；探针必须串行，不能与 UI/e2e 同时跑。

### 4.2 每次运行必须采集的字段

`deaths`、`seconds`、`totalDamage`、`firstDeath`、`damage100`、`hazard=命中/引爆(命中率)`、`killers`。
缺任一字段说明探针版本或页面快照退化，该批数据作废。

### 4.3 判读规则（先写死，避免事后找理由）

1. **闸门**：任何一次运行 deaths > 6 或 seconds > 900 → 该批失败，先查探针/页面报错，不接受「偶发」。
2. **难度看 `totalDamage` 中位，不看 `damage100`**：后者会被通关效率抵消（攻击变低 → 少撤退喝药 → 战斗变短）。
3. **职业同级**：死亡中位差 ≤1 且总承伤中位差 ≤30% → 判同级；超过则标记「职业偏斜」。
4. **峰值候选**：某关死亡中位 ≥4，或总承伤比相邻已测关高 30% 以上 → 进入阶段 B 诊断。
5. **零死亡**：8 次全 0 死记为「偏轻松」，是否处理由用户决策（见第九节）。
6. **跨批比较只比中位与分布**，不逐次对齐：种子只锁 `Math.random`，锁不住帧时序。

## 五、阶段 B：修正案验证（依赖阶段 A 与用户决策）

A/B 铁律：**一次只动一个系数**、同一 seed 区间、同一探针版本、改动前后各 n=8；不达标就回滚，不叠加第二个改动救场。

### B1 第 75 关拉长 `specialInterval`（4.63 → 5.2s）

- 前提：用户决定战士仍值得动（当前中位 3 死，闸门内）。
- 目标：战士每趟引爆从 55 次降到约 45 次，总承伤下降 ≥10%。
- 放行：战士死亡中位 −1 或总承伤 −10%；**同时**法师死亡中位不得降到 0（当前 1）、总承伤降幅 ≤20%。
- 否决：法师变零死亡或总承伤降幅 >20% → 回滚；改用其他手段（如只降 `sting` 追踪频率）另立方案。

### B2 第 30 关法师 `attackMult 0.88` 回调

- 前提：法师总承伤 1879 仅为战士 3420 的 55%。
- 候选：0.88 → 0.94（温和）或 1.0（完全回调）。
- 放行：法师总承伤回到战士的 ≥70%，且死亡中位 ≤3（闸门 6 的一半）。
- 否决：死亡中位 ≥4 → 回滚到 0.88。
- 提醒：0.8.1 已证明 0.88 对战士合适，本项只能改法师单独系数；现有修正表是**关卡级**，不能按职业分，
  若要按职业调，需扩展 schema 并新增单测守卫——这本身是一次结构性改动，先决策再动手。

### B3 第 60 / 90 关「零死亡」上调

- 现状：战士两关 8 次全零死，总承伤 2904 / 2757，明显低于第 30 关。
- 若用户判「太轻松」：现有 `attackMult` 单测只允许 (0.8, 1)，**上调必须先改 schema 与断言区间**（如 (0.8, 1.2) 并写明理由），
  不允许绕过测试直接写 >1。
- 放行：上调后两关死亡中位 1–2，且第 30 关仍高于它们；若第 60 关超过第 30 关，说明曲线倒挂，回滚。

| 项 | 放行标准 | 失败处理 |
|---|---|---|
| verify | 162 单测全绿、格式零差异 | 阻断提交，先修 |
| UI 六项 | 全部 PASS | 保留控制台输出与截图，定位到具体断言 |

| balance | 退出码 0，无结构性失衡输出 | 记录 CSV，数值改动必须复跑 |

e2e 走 `fast=1`（玩家伤害 ×25），**只能证明功能可通关，不能作为难度证据**。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 种子锁不住帧时序 | 同 seed 逐次仍不可复现 | 只比中位/分布；n≥8；跨批只作趋势 |
| n 太小判不了小改动 | 15% 级调整淹没在噪声里 | 目标效果 <20% 时 n 提到 16，或改用 `totalDamage` + 命中率 |
| 探针≠真人 | 高危结论可能是操作模型产物 | 死亡中位 ≥4 的关必须桌面手动试玩抽样 |
| `damage100` 被效率抵消 | 误判「没变简单」 | 难度结论一律以 `totalDamage` 为准 |
| 沙箱重置 | `node_modules`、浏览器丢失 | 开场 `npm install` + 镜像装 chromium + `install-deps` |
| e2e fast 模式 | 高估玩家输出 | 只作功能回归，不作难度证据 |
| 隧道/沙箱生命周期 | 公网地址失效 | 记录重启步骤；每次重启重新跑 a–d |
| API Key 泄露 | 账号被滥用 | 只走环境变量；不进仓库、不进日志；泄露即轮换 |

## 九、执行顺序与依赖

```text
每次提交：L0 + L1
            │
阶段 A（数据补齐）──► 用户决策（第九节）──► 阶段 B（A/B）──► 阶段 C（发布前全量）
            │
            └──► 阶段 D（部署验收，可与 A 并行，不参与难度判定）
```

阶段 A 未完成前不启动 B：没有道士与 60 / 90 关基线，任何「全局调整」都可能把一个未知职业推过闸门。
