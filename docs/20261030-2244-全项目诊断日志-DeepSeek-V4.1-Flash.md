# 全项目诊断日志：让「出了问题」直接看日志定位（0.8.6 → 0.8.7）

日期：2026-10-30 22:44
模型：DeepSeek-V4.1-Flash
版本：0.8.6（承伤诊断）/ 0.8.7（结构化日志）

## 为什么做

难度调优到第 75 关时，结论已经能写出来，但过程一直靠「探针数字 + 事后推理」：为什么这趟死了？是怪打死的、红圈炸死的，还是毒跳死的？为什么玩家说「按了没反应」？为什么存档读出来属性不对？旧代码里这些都只有 `console.warn` 或干脆静默吞掉，**复现成本高、现场留不下来**。

用户的要求很明确：不是给某几处加日志，而是**整个项目都加、细节足够多，以后出问题直接看日志就知道是哪出的问题**。因此 0.8.7 做的是基础设施，而不是零散埋点。

## 0.8.6 承伤诊断（日志的前置铺垫）

在日志系统之前，先给 `state` 挂了只读诊断容器 `diagnostics`（`runtime.js` 的 `createDiagnostics`），不参与结算、不写存档：

```js
damage: { monster: 0, hazard: 0, poison: 0 }   // 各来源累计伤害
hits:   { monster: 0, hazard: 0, poison: 0 }   // 各来源命中次数
hazards: { [kind]: { spawned, detonated, hit, damage } }
deaths: [ { killer, bossHpPct, bossPhase, poison, underfoot, ... } ]  // 最多 20 条
```

探针据此输出 `sources=怪N(%)/区N(%)/毒N(%)`、`hazardKinds=形态命中/引爆`、`deathCtx=死时首领血量/阶段/毒层/脚下危险区`。它的局限是**只能回答「哪一类伤害」**，回答不了「哪一次、在哪个分支、为什么没生效」——这正是 0.8.7 要补的。

## 0.8.7 日志基础设施（game/src/logger.js）

零依赖模块，Node 单测可直接导入。核心设计：

| 能力 | 实现 | 目的 |
|---|---|---|
| 分级 | `debug / info / warn / error` | 生产默认 info；`?log=debug` 或 `?e2e=1` 开 debug |
| 分类 | `cat` 字段（map / combat / skill / drop / save / shop / travel / equipment / item / hud / input / keybind / audio / perf / boot / runtime / abyss / difficulty / level） | 可按类别 dump，排查时先缩范围 |
| 环形缓冲 | 容量 600，满了丢最旧并累计 `dropped` | 不阻塞主循环、不写 localStorage（避免配额与存档污染） |
| 采样 | `logSample(key, every, ...)` | 高频事件（伤害、毒跳、被动触发）保留趋势但不刷爆缓冲 |
| 节流 | `logThrottled(key, ms, ...)` | 每帧都可能触发的事件（慢帧、按键、冷却提示）只按窗口记一次 |
| 全局上下文 | `setLogContext(() => ({ map, stage, cls, lv, hp, maxHp, frame, abyss, diff }))` | 每条日志自动带现场；provider 抛错时降级为 `ctxError`，日志本身不能打崩游戏 |
| 异常兜底 | `installGlobalErrorHooks()`：`error` + `unhandledrejection`，同错误只记一次 | 页面白屏但控制台为空时仍有 `[runtime] uncaught` |
| 浏览器入口 | `window.__ONEKNIFE_LOG__ = { dump, text, stats, clear, config }` | 控制台一行 `__ONEKNIFE_LOG__.text({limit:100})` 拿到最近日志 |
| E2E 入口 | `__ONEKNIFE_E2E__.logs / logsText / logStats / configureLog` | 探针 / 用例可直接读结构化日志 |

配置在模块加载时按 URL 决定：`?log=debug` 显式开详细日志并镜像控制台；`?e2e=1` 默认 debug 但**不镜像控制台**（逐条 `console` 会拖慢探针）；普通玩家默认 info。

## 关键口径：毛伤害 ≠ 净承伤

`diagnostics.damage` 是每次结算累计的**毛伤害**（含被盾吸收、被减伤被动吃掉的部分）；探针的 `totalDamage` 是采样时只统计 hp 下降的**净损失**。两者不可相加，冒烟实测毛 2239 / 净 1277。日志里 `playerHit.mitigated` 是两者之差，专门用来回答「为什么打不动」。

## 怎么用

1. 人手调试：地址加 `?log=debug`，控制台执行 `__ONEKNIFE_LOG__.text({ limit: 100 })`；按类别过滤 `__ONEKNIFE_LOG__.text({ category: "combat" })`。
2. 探针 / E2E 失败：`tests/difficulty-probe.cjs` 现在会在失败的 `catch` 里 dump 最近 120 条浏览器日志（`[探针失败现场]`），不用重跑复现。
3. 用例断言：`window.__ONEKNIFE_E2E__.logs({ level: "warn", limit: 20 })` 直接拿结构化条目。

## 单测发现并修掉的 bug

`logThrottled` 原实现用 `throttles.get(key) || 0` 判断上次时间。`performance.now()` 从页面 / 进程启动开始计时，**启动后 1 秒内的第一次调用会被误判成「窗口内重复」而丢掉**——正好会吞掉最关键的启动期日志。改为 `last !== undefined` 判断。`tests/unit/logger.test.mjs` 的 9 条用例（级别过滤 / 环形缓冲 / 采样 / 节流 / 上下文异常安全 / 文本导出 / 清理 / 异常钩子幂等 / 控制台入口）覆盖了这条路径。

## 经验

1. **日志是基础设施，不是调试残留**：分级 + 采样 + 节流 + 上下文四件套缺一不可，否则要么刷爆缓冲区，要么关键现场没有上下文。
2. **性能敏感路径只采样 / 节流**：`?e2e=1` 开 debug 但不镜像 console，避免探针被日志拖慢导致数据失真。
3. **日志本身要有兜底**：上下文 provider 抛错、控制台被重定向、localStorage 抛错都不能让主循环崩掉。
4. **单测要覆盖「第一次调用」**：节流 / 缓存类逻辑最容易在启动早期出错，而启动期恰恰是最需要日志的时候。
