## 二、为什么用 `main → work`，而不是 `work → main`

1. `work` 是当前玩法主线，提交数、近期验证和发布节奏都以它为准；把 `main` 并进来只需要解决一次分叉。
2. `main` 的价值集中在**可独立搬运的资产、工具和统计修复**，不依赖 `work` 的近期重构；反向合并会把 49 个玩法提交重新落到一条旧线上，冲突面更大。
3. 合并用 `--no-ff` 保留两条线的分叉记录，后续能一眼看出 0.8.77 是汇合点，而不是把 49 个提交假装成线性历史。
4. 不使用 rebase：两条线都已推送远端，改写单边历史会让协作者和部署端同时失联；历史清理只在最后统一做一次。

冲突文件 8 个：`.gitignore`、`README.md`、`VERSION`、`game/src/main.js`、`game/sw.js`、`package.json`、`文档索引.md`、`经验/01-工程与测试经验.md`。

| 文件 | 处理 |
|---|---|
| `.gitignore` | 取 `work` 版本，补 `.trae-html-share-packages/` 忽略 |
| `README.md` | 取 `work` 版本，合并后再补 0.8.77 段落 |
| `VERSION` / `package.json` / `package-lock.json` | 统一升 0.8.77 |
| `game/sw.js` | 缓存名改 `oneknife999-v0.8.77` |
| `game/src/main.js` | 以 `work` 为主，手工补回 `main` 的 6 处关键改动 |
| `文档索引.md` | 两边入口取并集，保留 `main` 的 0.8.43 统计文档与 6 份新增文档 |
| `经验/01-工程与测试经验.md` | 两边经验取并集，保留 `main` 的统计口径经验 |

`game/src/main.js` 不是简单“取 work”就能收工。`main` 的以下改动必须保留，否则自动合并进来的 `tools/playthrough.cjs` 会读到空字段：

- import 从 `{ PASSIVE_FX, SKILL_FX }` 改为 `{ PASSIVE_FX, SKILL_FX, ULTIMATE_FX }`；
- `let lastTime = 0;` 后新增 `let potionsUsed = 0;`；
- `oneMoment()` 在 `state.player.charge = 0;` 后补 `fx.skillFx.push({ key: ULTIMATE_FX, ... })`；
- `usePotion()` 在 `state.player.potion -= 1;` 后补 `if (TEST_MODE) potionsUsed += 1;`；
- TEST_MODE 的 player 快照增加 `potionsUsed`；
- TEST_MODE 的 entity 快照增加 `deepTuned: Boolean(entity.deepTuned)`。

`potionsUsed` 是 0.8.43 统计修复的核心：`tools/playthrough.cjs` 已改成读 `snap.player.potionsUsed`。如果合并时只取 `work` 的 `main.js`，实跑统计里的 `potionUsed` 会变成 `NaN`，而且不会在单元测试里报错。

## 五、Git 历史垃圾清理

### 5.1 先测量，不按提交说明猜体积

`main` 的提交说明写“约 100MB 原始绿底图”，实测并不是：

| 路径 | 对象数 | 实际字节 |
|---|---:|---:|
| `.trae-html-share-packages/` | 2 | 6,007,318（约 5.73 MiB） |
| `tmp/` | 47 | 5,439,001（约 5.19 MiB） |
| `.screenshots/.tmp/` | 1 个实际 blob | 296,446（约 0.28 MiB） |
| 合计 | — | 约 11.2 MiB |

三组都已不在当前工作树，只存在于历史对象。`美术素材-CogView/*.zip` 是正式交付物，不进入本次清理。

### 5.2 备份

清理前执行：

```bash
git bundle create /home/user/backups/oneknife999-pre-merge-cleanup-20261123-2120.bundle --all
```

bundle 约 289MB，包含清理前的全部 refs。历史改写后旧 SHA 全部失效，这个 bundle 是唯一完整回滚入口。

### 5.3 改写

`git filter-repo` 未安装，使用 Git 自带的 `filter-branch`：

```bash
git filter-branch --force --index-filter \
  'git rm -r --cached --ignore-unmatch .trae-html-share-packages tmp .screenshots/.tmp' \
  --prune-empty --tag-name-filter cat -- --all
```

执行后清理 `refs/original`、过期 reflog，并 `git gc --prune=now`。随后同时强推 GitHub 与 GitCode 的 `work` 和 `main`。

### 5.4 远端过期分支

GitHub 还留着 `deploy/0.8.6`（0.8.6）和 `trae/agent-SYLj24`（0.8.7），都落后 `main` 51 个提交，且可能让旧垃圾对象继续可达。本次一并删除；GitCode 侧没有这两个分支，只需删除 GitHub 上的两个 ref。

## 六、验证

```text
npm run format                 通过

npm run test:ui:status          desktop / mobile / mobile-sm / mobile-xs 四视口通过
npm run test:ui:status-real     中毒 / 眩晕 / 减速 / 致盲 / 破甲 / 移动端 6 例通过
```

合并后第一次跑 `test:ui:status-real` 时，减速用例出现 `lastKiller=矿脉蝙蝠`（上一场眩晕怪）而 `slowTimer>0` 的假阳性。根因是等待条件只检查状态计时，且 `loadMap` 没有清 `lastKiller`；现已改为：

- `loadMap` 重置 `state.player.lastKiller = null`；
- `waitForStatus` 同时要求状态计时与 `lastKiller === 本次目标名`。

这样上一场的残留计时或旧命中者不可能再让用例提前暂停。

## 七、代价与回滚

- 历史改写后，GitHub / GitCode 上的所有旧 SHA 都不可达；其他机器上的克隆必须 `git fetch --all --prune` 后 `git reset --hard origin/work`，不能直接 pull。
- 回滚只能从上面的 bundle 恢复；恢复前先确认没有把新提交只留在被改写后的本地。
- 强推后要重新检查远端 `work` / `main` 指向、GitHub Actions（如存在）和 Instabox 的跟踪分支。
- 远端分支删除后，旧的部署记录和分享链接可能仍指向旧 SHA；需要更新部署端或重新发布。
