# 贴图缓存内存治理（0.8.41）

- 模型：豆包
- 时间：2026-11-20 04:10
- 版本：0.8.40 → 0.8.41
- 触发来源：上一轮真实速度实玩报告里「云主机 4GB 内存，连续跑 4–5 关浏览器就被杀」一句。用户要求「你来解决，避免用户也遇到」，因此按产品缺陷处理，而不是当成环境限制绕过。

## 一、现象与初判

实玩脚本（Playwright + Chromium）连续推进时，跑到第 4–5 关渲染进程就被 OOM Killer 杀掉；单关单独跑完全正常。最初的怀疑是 JS 堆泄漏，但实测否定：

| 观测点 | 结果 |
| --- | --- |
| CDP `Performance.getMetrics` 的 `JSHeapUsedSize` | 单关 6–10MB，连跑两关仍 9–10MB，不随关卡增长 |
| `state.logs` | 只保留 8 条，DOM 日志不是泄漏源 |
| `state.drops / particles / texts / hazards` | 每次进图重置，不累积 |
| 渲染进程 RSS | 每关稳定上涨约 250–300MB，与关卡数线性相关 |

结论：内存在 JS 堆之外，属于渲染层的贴图缓存。

## 二、根因

`game/src/render.js` 的 `spriteCache` / `tintCache` 是「按 key 永久缓存」的实现，从不淘汰。素材库中的怪物动作帧是 2048×2048 的 PNG：

- 单张解码后 = 2048 × 2048 × 4B ≈ 16MB；
- 一关 4 种怪 × 4 帧（idle/walk/attack/hit）= 16 张 ≈ 256MB；
- 连跑 4–5 关累计超过 1GB，4GB 机器（乃至 8GB 机器同时开其它应用）都会被拖爆。

素材库静态统计：628 张 PNG 解码约 504MB，77 张 JPG 约 361MB，全部驻留的理论上限约 865MB。这不是云主机特有的问题，真实玩家连续玩多关同样会遇到，只是机器内存大小决定崩溃到来的早晚。

## 三、修复方案（render.js）

1. **按用途降采样**：`spriteMaxSide(key)` 按 key 前缀给出最大边——`map-bg-` 2048、`chapter-bg-` 1280、`boss-` 512、`ui-/icon-` 128、其余 256。解码完成后把原 Image 画进目标尺寸的 canvas，随后 `img.src = ""` 并解绑 `onload/onerror`，让 2048 解码位图立刻可回收。只降不升，不会放大低分辨率素材。
2. **字节预算 + LRU**：`SPRITE_BUDGET_BYTES = 128MB`、`TINT_BUDGET_BYTES = 24MB`。命中缓存时把条目移到 Map 队尾，超预算时从队首淘汰，淘汰时对 canvas 做 `width/height = 0` 主动清零像素内存。
3. **并发解码上限**：`MAX_IN_FLIGHT = 6`，其余请求进 `spriteQueue` 排队，避免一关十几张 2048 图同时解码造成的瞬时峰值。
4. **可观测性**：导出 `spriteCacheStats()`（`sprites/spriteMB/tints/tintMB/inFlight`），并在 `main.js` 的 `window.__ONEKNIFE_E2E__` 上暴露 `spriteStats`，供自动化回归核对。

修复过程中踩过两个坑，均已修掉：

- 首版算出了 `entry.bytes` 却没有累加到 `spriteBytes`，统计恒为 0MB；
- 降采样后 `img.src = ""` 会再次触发 error 回调，`spriteInFlight` 被重复递减到 −3；现在用 `entry.finished` 保证只结算一次，清空 src 前先解绑回调，计数再加 `Math.max(0, …)` 兜底。

## 四、验证

单关冒烟（warrior，第 1 关）：

```
spriteStats = {sprites:32, spriteMB:12.8, tints:0, tintMB:0, inFlight:0}
```

修复前同口径单关至少 268MB。两关连跑后 `sprites:42 / spriteMB:19.1 / tints:4 / tintMB:0.4`，JS 堆仍约 10MB，无 404、无页面报错。

`npm run verify` 225/225 全绿（Prettier 已对改动的 `render.js` / `main.js` 重新格式化）。

## 五、残余风险与后续

- 本次只治理了 Canvas 贴图缓存。DOM 侧 `<img>`（装备图标、首领情报头像等）仍由浏览器自身的图片缓存管理，长时间游玩是否会累积需要用 `Memory.getDOMCounters` 继续观察。
- 素材文件本身仍是 2048 大图，首次解码的瞬时峰值仍存在（已被并发上限压到 6 张）。彻底方案是把素材文件物理缩到显示所需尺寸（怪物 512、首领立绘 512、章节图 1280），可同时降低包体、网络与解码成本，待评估后执行。
- 压测脚本 `tools/playthrough.cjs` 的 `spriteStats` 与 `heapMB` 采样可作为后续回归的固定观察点。
