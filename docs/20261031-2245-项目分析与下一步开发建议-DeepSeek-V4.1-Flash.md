# 《一刀999》0.8.8 项目整体分析与下一步开发建议

- 分析基线：`atomgit.com/laotongtian/oneknife999` `main` @ `80b1c30`（0.8.8）
- 分析范围：代码结构、功能完整度、测试与质量、部署形态、内容产能、已知缺陷
- 结论先行：**核心闭环已闭环、质量基座可用，但缺少「持续验证」与「内容深度」两层能力**。下一步应优先补 CI 与真机验证，再上精英系统与战斗深度，最后才考虑后端与商业化。

### 5. 优势与短板

**优势**
- 零依赖、零构建，部署成本极低（一个静态目录 + 一条隧道）
- 数值与随机注入设计良好，探针与单测可复用
- 文档治理严格（设计分卷 + 时间戳快照 + 经验库），项目可维护性高于同规模原型

**短板**
- 没有持续集成，回归全部依赖人工，版本越多风险越大
- 移动端只做过 Chromium 仿真，真机（iOS Safari / 微信）未验证
- 内容深度不足：精英、战斗手感、图鉴目标感、深层差异化
- 无后端，多人、排行榜、防作弊、云存档都无从谈起

## 二、下一步开发建议

按「投入产出比」与「当前最大体验缺口」排序，分三个阶段。

### 阶段 A：质量基座（1–2 周，优先级最高）

#### A1. CI 流水线（3 人日）★最高优先

- **现状**：无 CI，提交后是否回归全凭人工；本轮已出现「改了测试断言但没人知道」的情况。
- **方案**：GitCode/Actions 流水线，两步：
  - `fast`（每次 push）：`npm run verify`（check + format + 167 单测），5 分钟内
  - `full`（合并前 / 每日）：6 项 UI + `test:ui:timeline`，缓存 `~/.cache/ms-playwright`
- **验收**：任意 PR 都能看到 6 项绿标；失败时附 `tests/` 产物与截图。
- **风险**：CI 环境的 Chromium 版本需锁定（仓库当前 `^1.62.1`，本地实测 1.63 与缓存浏览器不匹配，需固定 `playwright@1.62.1`）。

#### A2. 百图分段回归（2 人日）

- **现状**：单页跑 100 关会随机崩；已用 25 关重建 context 规避，但未固化。
- **方案**：`e2e-100-shots.cjs` 拆成 4 段（1–25/26–50/51–75/76–100），每段独立存储 `storageState`；每周一次，产出 `STAGE STATS`。
- **验收**：4 段全部到达 checkpoint，`WARN` 为 0，最终文案「百图征途已通关 / 全部完成」。

#### A3. 存档健壮性（2 人日）

- **现状**：导入不校验金币上限；schema 变更靠手工迁移。
- **方案**：
  - `sanitizeSavedGame` 对金币/等级/数量/强化等级做区间钳制，并补单测
  - 建立 v2→v4、v3→v4、未来 v5 的迁移矩阵（表驱动），每次改 schema 必加迁移用例
- **验收**：篡改金币 123456 被钳制到上限并提示；迁移用例覆盖 3 个版本。

#### A4. 体验缺陷收口（2 人日）

- toast 队列化（购买成功不再被覆盖）
- 召唤骨卫与 README 对齐（改为脚下召唤或改文案）
- 装备槽空位提示增加内边距
- 41–46 关复核：用 `difficulty-probe` 分段采样，>4 死触发调平（优先看行为密度与药水投放）

#### A5. 经济模型补全（3 人日）

- **现状**：`balance-sim` 只模拟战斗掉落，未含商店购买、强化、重铸、难度品质提档。
- **方案**：把金币产出/消耗（药水、矿石、卷轴、强化费）纳入模拟，输出 100 关的金币曲线与装备战力曲线。
- **验收**：三条曲线单调不爆（金币不出现后期富余、强化不出现断档），与实测金币基线（第 10 关 ≈13k、第 40 关 ≈68k）误差 < 20%。

#### A6. 移动端真机验证（2 人日）

- **现状**：只有 Chromium 移动仿真（390/360/768）。
- **方案**：iOS Safari、Android Chrome、微信内置浏览器各跑 1 次核心闭环（开局→1 关→商店→存档刷新），记录摇杆/长按/安全区问题。
- **验收**：三端均能完成开局与首关，无横向滚动、无按钮不可点。

> 阶段 A 完成标准：CI 绿、百图 4 段可复跑、导入上限生效、经济曲线可控、三端真机通过。

### 阶段 B：内容深度（3–6 周）

#### B1. 精英系统（8 人日）★内容侧最高优先

- **现状**：普通怪与精英共用同一套被动，缺少「精英」这一层。
- **方案**：按 `docs/04` 的八条词缀（狂怒/护卫/回响/分裂/追猎/守财/净化/毒爆）实现，每条 = 2 条行为原语 + 1 条奖励词缀；互斥规则（瞬移×不可选中、反伤×吸血、沉默×缴械）；每条词缀必须有 ≥0.5s 可读提示（复用铭牌/飘字系统）。
- **涉及**：`monster-abilities.js`（词缀表）、`maps.js`（精英标记）、`render.js`（词缀提示）、`drops.js`（精英奖励）。
- **验收**：第 15/45/75 关各出现 ≥1 组精英；探针死亡中位数 ≤6；铭牌遮挡审计仍为 0。

#### B2. 战斗深度：施法硬直与打断（6 人日）

- **现状**：技能瞬发，无硬直/打断，战斗节奏偏「哪里亮了点哪里」。
- **方案**：为 3–4 技能加前摇（0.2–0.5s）+ 可被打断窗口（受击/控制），配输入缓冲（casting 期间缓存下一次指令）；UI 给施法条。
- **验收**：打断后技能不进冷却、资源返还；`ui-render-input-regression` 输入不丢；三职业各 1 段手感录像/截图。

#### B3. 图鉴收集奖励（4 人日）

- **现状**：图鉴只有展示。
- **方案**：先做**零数值**的称号与外观（集齐一章解锁称号/边框），验证玩家反馈后再评估属性加成（加成需进 `balance-sim`）。
- **验收**：集齐第 1 章触发称号；不影响任何战斗数值（单测断言攻击/生命不变）。

#### B4. 无尽深层程序化地形（6 人日）

- **现状**：深层复用 100 图地形，只有数值成长。
- **方案**：`generatedLayout(stageNumber, chapter)` 扩展为 `(seed = floor, tier)`，层数作种子生成营地/道路/怪物分区；每 5 层一个精英层，每 10 层首领层。
- **验收**：同一层号生成结果确定（快照测试）；不同层拓扑差异 > 阈值；深层 10 层连续可玩。

#### B5. 兜底图透明化与素材接入（5 人日）

- **现状**：96 张生成图 + 543 素材，无法判断哪些图是「临时兜底」。
- **方案**：在 `catalog` 输出 `artTier`（handcrafted / generated / fallback），统计每章素材缺口，按章节批量补图。
- **验收**：`artTier` 可查询；每章至少手工图占比 ≥20%；资源 404 仍为 0。

### 阶段 C：架构与商业化预研（2–3 月）

#### C1. 最小后端（10–15 人日）

- **目标**：云存档 + 排行榜 + 服务端权威校验（反作弊）。
- **方案**：先做「只读+写入校验」两层：
  - `POST /save`（服务端校验金币/等级/装备合法性，拒绝超上限）
  - `GET /leaderboard`（按最深关卡 + 战力）
- **验收**：本地改档无法上传；排行榜 Top100 可查；断网可离线玩、联网后合并。
- **风险**：会打破「零依赖静态部署」的优势，需明确「离线优先」策略。

#### C2. 埋点与漏斗（5 人日）

- **方案**：复用 0.8.8 的时间线，扩展为可上报事件（开局/首杀/首死/首次商店/第 10 关/流失点），批量上报。
- **验收**：能回答「首关流失率」「41–46 关死亡分布」「商店首次购买率」。

#### C3. 性能预算与资源管线（8 人日）

- **现状**：59.8 FPS、JS 堆 6MB，单机良好；素材 543 个全量加载。
- **方案**：首屏资源预算（< 1.5s / < 3MB）、按章节懒加载、Canvas 图层缓存、大图 WebP。
- **验收**：3G 弱网首屏 < 5s；移动端 FPS ≥ 50。

## 五、不建议现在做

| 事项 | 理由 |
|---|---|
| 引入 React/Vue 或构建工具 | 当前零依赖部署是最大优势，重构收益低、风险高 |
| 实时多人战斗 | 需要帧同步/状态同步，成本 ≥ 3 人月，当前用户量不足以支撑 |
| 付费与内购 | 原型阶段，先验证留存再谈商业化 |
| 全量 100 关素材补齐 | 应先做 `artTier` 分层，按章节 ROI 补图，避免一次性铺开 |

## 七、结论

项目已经越过「能不能玩」的阶段，当前瓶颈不在功能数量，而在**持续验证能力**与**内容纵深**：

- 先把 CI、百图分段、真机、经济模型补齐（阶段 A），把「每次改动都可信」变成常态；
- 再用精英系统与施法硬直提升战斗纵深（阶段 B），这是玩家最直接感知的差异；
- 后端与商业化留到留存数据出来之后再投（阶段 C）。

若只能做一件事：**建 CI 并把百图拆成 4 段跑起来**——它决定后续所有迭代的可信度。
