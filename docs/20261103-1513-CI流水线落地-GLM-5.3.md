# CI 流水线落地

## 背景

0.8.8 轮的《项目分析与下一步开发建议》把 CI 列为最高优先（A1），两轮规划过去仍未落地，回归全凭人工触发。本轮（0.8.17）补上：push / PR 自动跑「静态检查 + 200 单测 + 7 项浏览器回归」。

## 方案

`.github/workflows/ci.yml`，两段式：

1. **verify job**（无浏览器，约 1 分钟）：`npm ci` → `npm run verify`（`node --check` 全模块 + prettier + `node --test` 200 单测）。
2. **ui job 矩阵**（依赖 verify）：7 项浏览器回归 `ui / ui:layout / ui:levelup / ui:regression / ui:nameplate / ui:abilities / ui:elite`，`fail-fast: false` 保证一次看到全部失败项。

关键约定：

- 浏览器统一 `ONEKNIFE_CHANNEL=chromium`（playwright 自带），规避宿主 Chrome 版本漂移——0.8.8 文档实测过 1.63 与缓存浏览器不匹配的问题，CI 每次全新安装则彻底绕开。
- 静态服务按 tests/ 默认约定起在 `127.0.0.1:4174`（`python3 -m http.server --directory game`），与本地跑法完全一致，测试零改动。
- 缓存 `npm`，`node 22`，job 超时 10/15 分钟。

## 验收

- push main 后 Actions 自动触发，verify + 7 项 ui 全绿。
- 失败时矩阵逐项标红（非 fail-fast），日志可直接定位。

## 已知边界

- **GitCode 不执行 GitHub Actions**：CI 只在 GitHub 侧生效；GitCode 仍是镜像。若双端都要门禁，需要另接 GitCode 流水线（暂缓）。
- workflow 文件的推送需要带 `workflow` 权限的令牌；普通 PAT 推代码没问题，推 `.github/workflows/` 可能被拒（GitHub 的 OAuth App 限制）。若被拒：其余提交照常，workflow 文件需要用带权限的令牌补推一次。
- e2e 百图 / 难度探针 / 平衡模拟**不进 CI**（单跑 30–90 分钟，且云环境会挂起中断）——百图分段回归是下一轮（P0-2）的工作，届时评估是否加 nightly 任务。

## 后续（P0 剩余）

- P0-2：百图分段回归 + 断点续跑（e2e 两次分别死于 18/45 关的实测证据已在 0.8.16 报告里）。
- P0-3：素材瘦身（41 个 >1MB 的 PNG，最大单帧 5.1MB，总 172MB）。
