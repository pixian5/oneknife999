## 二、已测量但**未采纳**的数值实验（F2 前半，已回滚）

在 `maps.js` 上试了「怪血成长 0.0097→0.045/0.075」「攻击成长 0.32→0.8/1.6/2.4/3.2」「清怪数 5–8→7–13」的组合，用 `balance-sim.mjs`（真实速度、种子可复现）+ `balance-envelope.mjs` 打分：

| hp成长 | 攻击成长 | 清怪 | 战士死亡 | 零死图 | 后90关 | Boss占比 | 药水 | 终局金币 |

| 0.075 | 0.8 | A(8/8/7/8/10/12) | 8 | 97 | 28.5s | 47% | 8985 | 29750 |
| 0.075 | 2.4 | A | 26 | 85 | 30.9s | 47% | 10508 | 36099 |

结论：`后90关 30–48s` 与 `Boss 40–58%` 两个封套项**可以同时达标**（0.075 + 攻击 2.4），但代价是：
- 章节死亡分布仍是 `[8 0 0 0 0 0 0 1 6 11]` —— 第 2–7 章依然零死亡，「每章 ≥1 死」不成立；
- 三职业总时长极差 1.43×（>1.25×），战士/法师药水比 164×（>3×）；
- 终局金币 3.6 万（>1.5 万，需要 F5 消费出口）。

也就是说：单靠 F2 的「血/攻/清怪」三个旋钮**修不好职业差与难度曲线**，必须先动 F4 的承伤结构（战士 def 22→28、满破势减伤 12%、道士召唤 −8%）与 F5/F6。因此本轮**没有**把 F2 的数值写进代码，`maps.js` 保持 0.8.39 原值。

## 七、职业平衡的关键约束（本轮实测，写下来免得下次再撞）

- `computeDamage` 的 `base = hero.attack + level*4 + weaponPower*0.9 + setAttack`：深度 100 时等级项 160、武器项 ~250，**attack 41→50 只让总伤害涨约 2%**，所以"调 attack"对职业强度几乎无效（本轮实测 mage 57.3→57.3min 不变）。
- 法师 cd 0.86→0.70 也只从 57.3 降到 56.8min：瓶颈不在普攻频率，而在**技能循环/清怪效率**（技能倍率、法力、cd 2.5s）。
- 结论：F4 要动的是技能倍率与资源循环，而不是 attack/cd 小数值；动之前先用 `--strict` 量化，避免"改了没感觉"。
