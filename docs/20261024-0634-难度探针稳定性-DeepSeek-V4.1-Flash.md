# 0.3.9 难度探针稳定性（多次取中位数 + 提高喝药阈值）

## 问题

0.3.6 落地的非快进难度探针在第 15 关测出过 **0 死 / 75s、1 死 / 138s、5 死 / 251s** 三种结果，
而这三轮之间战斗逻辑没有任何改动。原因是探针本身存在正反馈放大：

1. 玩家死亡 → `loadMap(..., true)` 让首领**满血重置**，一次失误就让整场首领战重来；
2. 喝药阈值 55% 偏低，血量刚掉到 55% 时往往已经进入「下一次重击就死」的区间；
3. 单次结果被当作结论，读不出「数值回退」和「一次操作失误」的区别。

结果：探针只能在「是否卡死 / 是否超闸门」这一层当门禁用，无法作为数值回归。

## 实现

### 1. `ONEKNIFE_PROBE_RUNS`（默认 3）

每关重复 N 次，每次**新建 context + page**（隔离虚拟时钟与存档写回，沿用 0.3.6 的做法），
取死亡数与耗时中位数作为该关结果：

```js
const PROBE_RUNS = Math.max(1, Number(process.env.ONEKNIFE_PROBE_RUNS || 3));
```

- 中位数（偶数个时取中间两个平均并四舍五入），输出形如
  `5:0死/50s[0死/50s,0死/52s,0死/49s]`；
- 判定改为**中位数闸门**：`deaths > MAX_DEATHS` 才失败；
- 单次超限只打印 `PROBE WARN`，不直接失败——否则 3 次里一次操作失误就会把整轮验证打红；
- **耗时仍是单次严格判定**（`seconds > MAX_SECONDS` 立即失败），因为它代表「关卡能否推进」，不存在「偶发」的说法。

### 2. 喝药阈值 55% → 65%

```js
if (guard % 3 === 0 && (snap.player.potion || 0) > 0 && snap.player.hp < maxHp * 0.65) await page.keyboard.press("q");
```

- 阈值提前 10 个百分点，落在「满血之外的第一次重击」之前；
- 检查频率从每 4 个循环改成每 3 个循环，减少「刚好错过喝药窗口」；
- 撤退阈值仍是 60% / 3 层毒——喝药 65% 早于撤退 60%，形成「先喝药、再考虑撤退」的层次，不会互相打架。

### 3. 打印格式

`PROBE START` / `PROBE RESULT` 增加 `run=1/3`，便于对照同一关的多次运行。

## 验证

`npm run test:difficulty`（默认 3 次）：

```
DIFFICULTY PROBE PASS runs=3
  stages=5:0死/38s[0死/50s,0死/38s,0死/38s]
         15:0死/52s[0死/52s,0死/53s,0死/36s]
  totalDeaths(median)=0
```

对照 0.3.6~0.3.8 的单次结果（同一套战斗数值）：

| 轮次 | 第 5 关 | 第 15 关 |
| --- | --- | --- |
| 0.3.6 | 0 死 / 59s | 0 死 / 52s |
| 0.3.7 | 0 死 / 51s | 1 死 / 138s |
| 0.3.8 | 0 死 / 52s | **5 死 / 251s** |
| 0.3.9（3 次中位数） | 0 死 / 38s | **0 死 / 52s**（三次分别 0/0/0 死，52/53/36s） |

三次运行零死亡且耗时离散度只有 ±17s，说明 0.3.8 的 5 死 / 251s 主要是**探针喝药太晚 + 死亡让首领回血重置**造成的自放大，而不是关卡难度变化。

全量验证：105 单测全绿、三视口冒烟 / 升级专项 / 渲染回归 PASS、perf 平均 5631.24 fps / p95 0.4ms / p99 0.7ms / 最差帧 5.5ms / 零长帧、百图 e2e 100/100（Lv.41、0 次死亡、100 个检查点 SAVED+RESTORED、终局金币 227870）。
