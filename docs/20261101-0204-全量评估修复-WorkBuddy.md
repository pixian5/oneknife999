# 0.8.11 全量评估问题修复：矮视口画布塌陷、战区实色、HUD 字号、perf 门禁稳定性与 41–50 关复核

- 日期：2026-11-01 02:04
- 执行：WorkBuddy（接手 0.8.10 全量评估后，按评估报告逐项修复）
- 上游评估：0.8.10 全量运行评估报告（169 单测 / 8 UI 回归 / 三职业百图闭环 / 多视口截图），发现 1 项 P1、3 项 P2、若干 P3。

## 一、修了什么

### P1 矮视口画布塌陷（最严重）

**现象**（评估实测）：`720×420` 下 `#gameCanvas` 高度为 **0**（画面完全不可见）；`320×568` 只剩约 56px；`1440×380` 约 102px。现有三视口冒烟（1440×900 / 390×844 / 360×640）覆盖不到这类高度。

**根因**：0.8.x 起 HUD 锁单屏——`html, body { height: 100%; overflow: hidden }`、`.app-shell { height: 100dvh; overflow: hidden }`、`.game-layout { height: calc(100dvh - 68px - 108px) }`、`.canvas-wrap { min-height: 0 }`。画布靠 flex 剩余高度分配，视口矮到一定程度剩余空间被顶栏 / 地图头 / 页脚 / 侧栏分完，画布被压成 0。`≤760px` 宽的移动端分支里动作条还会换行堆到 230px+（360×640 实测 234px，占屏 37%），进一步挤压。

**修复**（`game/game.css`，全部带注释说明动机）：

1. `@media (max-height: 620px)`：放开 `overflow` 裁剪改为按内容撑开 + 页面纵向滚动兜底，`canvas-wrap` 给绝对下限 `max(220px, 40dvh)`；`game-layout` 底部按固定动作条高度让位（124px）。
2. `@media (max-height: 480px)`：极矮视口（分屏 / 压扁窗口）下非核心装饰让位——隐藏地图眉题、页脚，压缩顶栏内边距、侧栏到 80px、画布下限 150px；动作条压成一行（nowrap + 缩小技能键 / 资源条）。
3. `@media (max-width: 760px) and (max-height: 760px)`：小屏 HUD 分级——顶栏收紧行高与按钮内边距（**不能用横向滚动**，按钮跑到视口外会直接触发 UI 契约失败，实测踩坑）、页脚「区域动态 / 坐标」与画布上的首领警报、目标卡重复直接隐藏、动作条压一行、`game-layout` 高度按压缩后的顶栏 / 动作条重算。

**修复后实测**（10 视口首屏可见画布高度，滚动兜底前）：

| 视口 | 修复前 | 修复后 |
|---|---:|---:|
| 720×420 | **0** | 253px |
| 320×568 | ~56 | 237px |
| 1440×380 | ~102 | 184px |
| 360×640 | 267 → 字号回归后 146 | 267px（滚动 0） |
| 390×844 / 1440×900 | 正常 | 不受影响 |

**踩坑记录**（三条都有测试背书）：
- 顶栏改 `flex-wrap: nowrap + overflow-x: auto` 让 4 个按钮溢出视口，`ui-smoke` 的「顶栏按钮不溢出且中心点可命中」当场拦截 → 改回换行 + 收紧内边距。
- 摇杆压到 52px 被 `ui-smoke` 的「摇杆 ≥60×60 触控最小尺寸」契约拦截 → 恢复 62px。
- 字号统一提升后 360×640 画布从 267 掉到 146（HUD 吃掉增量）→ 催生上面第 3 条小屏分级，回到 267。

### P2 生成地图首领战区实色块

**现象**：96 张生成地图的 `palette.special` 直接用章节实色（`#324b3c` 等），整块填充完全盖住底图，截图里像调试色块；4 张手工地图本来就是 rgba。

**修复**：`maps.js` 新增 `hexToRgba(hex, alpha)` 纯函数（非法输入原样透传），生成地图 palette 组装时 `special: hexToRgba(chapter.special, 0.45)`；**地标装饰仍用章节实色**（半透明会让地标几乎看不见）。第 30 关截图复核：战区半透明、底图纹理透出。新增 2 条单测（hexToRgba 合法性、100 图战区填充必须 rgba 且 0<alpha<1），单测 169 → **171**。

### P2 HUD 信息密度与 9px 小字

正文类小字 16 处 9px → 10/11px：地图目标卡（步骤标签 / 勾选项 / 描述）、动作条（目标副标题 / 技能副标题 / 药水数量 / 内力标签）、侧栏（实时标签 / 任务链节点 / 区域节点三级文字 / 任务奖励）、商店与图鉴计数、技能提示脚注。保留 7-8px 的只有装备格角标（slot-name / enhance / power 等）与技能点数字角标（紧凑角标不属于正文）。`test:ui:nameplate` 复跑 **9330 铭牌 0 遮挡**。

### P3 perf 门禁对首次长帧敏感

**现象**：`npm run perf` 偶发失败——8 次采样里 3 次出现 1 个 20ms+ 长帧（24.4 / 26.7 / 22.9ms），来源是 GC 与宿主调度抖动，预热只能压掉「首次进入」的部分。

**修复**（`tests/perf-probe.cjs`）：
1. 新增 `ONEKNIFE_PERF_WARMUP`（默认 1500ms）预热段：跑同样真实操作但整段丢弃帧数据。
2. 新增 `ONEKNIFE_PERF_ATTEMPTS`（默认 3）多段采样：每段独立 context，取达到门禁的那段；**真实性能回归会三段都超标仍失败，不会重跑放水**。报告带 `attempts` 明细（每段 over20/p99/worst），不隐藏抖动事实。

连跑 3 次 `ONEKNIFE_PERF_P99_MAX=12`（沙箱软件渲染阈值）：全 PASS，attempts 分布 2/1/2。

### P3 41–50 关死亡峰值复核（结论：不是真问题，未改数值）

评估报告 P3 提示 fast e2e 在 41/42/43/45/48/49/50 关有死亡峰值（最大单关 5 死），与历史记录的 41–46 关峰值一致，建议非快进复核。本轮跑三职业 × 7 关 × 2 runs = **42 次非快进采样**：

| 职业 | 各关死亡（两轮） | 单关中位最大 |
|---|---|---|
| 战士 | 41:0/0 42:0/1 43:4/0 45:0/0 48:0/0 49:3/2 50:0/0 | 2.0（第 43 关） |
| 法师 | 41:1/0 42:1/0 43:2/3 45:0/0 48:0/0 49:1/1 50:0/0 | 2.5（第 43 关） |
| 道士 | 41:0/0 42:1/0 43:1/3 45:0/0 48:0/0 49:0/0 50:0/0 | 2.0（第 43 关） |

**全部远低于 ≤6 死闸门**（整体死亡中位 0）。fast 模式的「41–50 峰值」在真实条件下不复现——再次验证 `?fast=1` 数据不能作为难度结论（项目铁律 1）。第 43 关法师 2.5 中位是本段最高，仍在闸门内，不动数值。样本量 2 次/关是局限，若后续要动第 43 关需先补 runs≥8。

## 三、没做什么（诚实边界）

- 第 43 关只跑了 runs=2；如要作为调平依据需补大样本。
- HUD「信息分级」只做了小屏（≤760px 宽）分支，桌面端同屏信息量未减（改动风险高，需要先有桌面布局回归基线）。
- 评估报告里的「性能硬门禁对首次长帧敏感」已用多段采样解决，但沙箱软件渲染的 p99 绝对值仍不可与本机比（铁律 6）。
- 精英系统、深层程序化地形、图鉴奖励等不在本轮范围。
