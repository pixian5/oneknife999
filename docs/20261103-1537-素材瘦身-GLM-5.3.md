# 0.8.18 素材瘦身（P0-3）

## 背景

172MB / 551 个素材是交付层最大隐患：41 个 PNG 超过 1MB，最大单帧（苔冠树精受击）5.12MB。首屏虽只拉 49 个请求，但第 2 章起按需加载这些巨帧，移动端弱网必卡。本轮对全部 >1MB 的 PNG 做调色板量化重编码——**保持 PNG 格式与透明通道，不改文件名，不引入构建链**（游戏仍是零构建纯静态）。

## 工具

新增 `tools/optimize-assets.mjs`（离线工具，依赖 sharp 单独安装、不进游戏依赖）：对超过阈值的 PNG 做 `palette 量化 + quality 82 + effort 9` 重编码；仅当新体积 < 原体积 88% 才落盘；逐文件输出对照表并自检尺寸一致。

## 结果

- **39 个文件重编码：102.5MB → 34.4MB（省 66%）**
- 素材总体积 **172MB → 104MB**；>1MB 文件 **41 → 18**
- 最大单帧：苔冠树精-hit 5.12MB → 2.00MB（-61%）；白骨射手-idle 3.80MB → 0.79MB（-77%）

## 质量验证（四道）

1. **重编码自检**：39 个文件逐个重读解码、尺寸一致才落盘。
2. **像素级对比**（flatten 黑底后逐字节）：前 5 大文件平均差 **1.2–1.4 / 255（≈0.5%）**，差异超 16 级的像素仅占 0.08–0.22%——肉眼不可辨。（直接对 RGBA 做 difference 会得到 ~64 的伪影，是透明区 RGB 垃圾值所致，不是真实差异。）
3. **线上分发确认**：公网地址 fetch 苔冠树精-hit = 200 / 1952KiB、白骨射手-idle = 200 / 774KiB，与磁盘新文件一致。
4. **Chromium 真解码**：39 个优化文件 `createImageBitmap` 全部成功（39/39），全程控制台 0 错误。
