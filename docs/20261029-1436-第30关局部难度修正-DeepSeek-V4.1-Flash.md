# 第 30 关局部难度修正（0.7.7）

- 日期：2026-10-29 14:36
- 模型：DeepSeek-V4.1-Flash
- 版本：0.7.6 → 0.7.7
- 内容：把「削全局形态系数」改为「只修出现死亡峰值的关卡」，用关卡级输出修正替代全局钝刀

## 一、决策依据

0.7.6 的致死来源统计给出两个事实：

1. 第 30 关的 53 次死亡集中在**本关攻击最高的四种怪 + 首领**（沙魂亡灵 95、炎蝠 98、石甲巨像 92、矿毒邪蛛 89–91），「形态」与「数值」是叠加的，不是单纯的形态问题；
2. 同一批数值下，第 60 / 75 / 90 关只有 0–2 死（0.7.2 数据）。**全局再削 `ranged` / `charge` 会把本来就轻松的图一起变简单**，是把尖峰压平、而不是修尖峰。

用户选择「只调第 30 关局部配置」。因此本轮新增关卡级修正表，**不动任何全局形态系数**。

## 二、机制：关卡局部难度修正

[maps.js](../../game/src/maps.js) 新增：

```js
export const MAP_DIFFICULTY_OVERRIDES = {
  30: { attackMult: 0.88, reason: "战士 n=8 死亡中位 7、承伤 5741/百秒；相邻关 60/75/90 为 0–2 死" }
};

export function mapDifficultyOverride(stageNumber) {
  return MAP_DIFFICULTY_OVERRIDES[stageNumber] || null;
}
```

`generatedMap()` 读取该表，把 `attackMult` 同时作用到该关**普通怪与首领的攻击力**：

- 普通怪：`attack = Math.round((70 + typeIndex * 2.785 + (stage-4)*0.32) * attackMult)`
- 首领：`attack = Math.round((112 + (stage-4)*0.42) * attackMult)`

只降输出、**不动生命**——耗时基本不变，承伤速率（`damage100`）成为干净的前后对照，也不会改变清怪节奏与装备掉落曲线。

关卡对象新增 `difficulty: { attackMult, reason }`，便于单测与后续排查；前 4 张手工图不参与生成曲线，不带该字段。

### 为什么选 0.88

目标是把承伤压到「闸门有余量」的程度。攻击力与承伤近似线性，0.88 对应约 −12%，留一点余量覆盖 ±17% 的采样波动。没有直接按 −10% 取值，是因为首领与地面危险区的伤害也会同步下降，实际降幅会略小于系数本身。（复测后发现 `damage100` 会被通关效率抵消，判定口径改为「每次通关的总承伤」，见第四节。）

## 三、单测守卫

新增用例「关卡局部难度修正：只作用于登记过的关卡，且不误伤相邻关」，锁住四件事：

1. 登记值合法：关号在 5–100、`attackMult ∈ (0.8, 1)`、必须写明 `reason`；
2. 只有登记关生效：未登记关一律 1.0，前 4 张手工图不得带 `difficulty`；
3. 修正确实有效：第 30 关最强普通怪与首领的攻击应**低于相邻的第 31 关**（否则修正等于没做）；
4. `mapDifficultyOverride(29) / (31)` 必须为 `null`，防止「改一关顺手带上下邻居」。

`npm run verify`：162 单测全绿（161 → 162）。

### 3.1 顺带修复：渲染回归的拾取断言失效

跑 `npm run test:ui:regression` 时第 2 步稳定失败（`拾取后面板未刷新`）。先在同一台机器上 `git stash` 掉本轮改动重跑——**0.7.6 的提交同样失败**，确认与本次难度修正无关，是用例自身失效：

- 0.4.4 起**装备必须站到 85px 内按 F 才能拾取**，而首领战的击退会把玩家推出该范围；
- 旧用例盲按 F，会弹出「附近没有可拾取物品」——这句话里**也含「拾取」二字**，被 `/拾取/` 判成拾取成功；
- 于是 `picked=true` 但什么都没捡到，后面的「面板必须刷新」自然失败。

修复方式（不放宽断言，而是让操作真的发生）：

1. `snapshot()` 补 `drops`（`id / x / y / name / slot`），用例据此找最近的**装备**掉落；
2. 新增 `walkToward()`，用键盘朝掉落点走到 60px 内再按 F；
3. 判定改为「背包 / 药水 / 金币 / 印记至少一项真的增加」，不再看 Toast 文案；
4. 拾取失败时朝掉落点再走一步重试（最多 12 次）。

修复后连续跑两次 `test:ui:regression` 均 PASS。

## 四、复测（战士 n=8，seed 2000–2007）

同一探针、同一组种子，只把第 30 关怪物 / 首领攻击降到 0.88 倍：

| seed | 死亡 | 耗时 | 首死 | 承伤/百秒 | 总承伤（≈承伤×耗时/100） |
|---|---:|---:|---:|---:|---:|
| 2000 | 3 | 70s | 55s | 5666 | 3966 |
| 2001 | 3 | 74s | 43s | 4926 | 3645 |
| 2002 | 5 | 92s | 18s | 4829 | 4443 |
| 2003 | 3 | 68s | 47s | 5615 | 3818 |
| 2004 | 5 | 111s | 56s | 4653 | 5165 |
| 2005 | 0 | 37s | — | 5881 | 2176 |
| 2006 | 6 | 96s | 53s | 5433 | 5216 |
| 2007 | 1 | 49s | 26s | 6178 | 3027 |
| **中位** | **3** | **72s** | **47s** | **5524** | **3892** |
| 0.7.6 基线 | 7 | 91s | 33s | 5741 | 5224 |

结论：

1. **死亡中位 7 → 3**（全距从 2–10 收到 0–6），首次死亡从 33s 推迟到 47s，通关耗时 91s → 72s。第 30 关从「压线」变成「有余量」，闸门（≤6）不再需要靠中位数勉强压住。
2. **`damage100` 只降了 3.8%，但总承伤降了 25.5%**——这不是修正无效，而是指标本身有混淆：攻击变低后玩家不再频繁撤退喝药，战斗时间缩短 21%，「单位时间的承伤」被效率提升抵消了。**判「关卡变简单」应该看「每次通关的总承伤」**（`damage100 × 耗时 / 100`），`damage100` 更适合作为「战斗中瞬时压力」的旁证。这条要在 0.7.6 的判定口径上修正过来。
3. 致死来源也随之分散（石甲巨像、巨虫、炎蝠仍会出现，但单次最多 2 次），没有再出现「同一种怪连杀 4 次」的情况（0.7.6 的 seed 2007 是沙魂亡灵 x4）。

## 五、这套机制以后怎么用

- **只登记实测出峰值的关卡**，每次登记必须写清 `reason`（数据来源：n≥8 的探针批次）；
- 判定主指标是**每次通关的总承伤**（本轮基线 5224 → 3892，−25.5%），`damage100` 只作旁证；死亡数作 ≤6 闸门；
- 若「局部修正」也压不住，再考虑该关的刷怪档位 / 排布（`spawnTier` 与 `monsterSpawns`），而不是回头动全局 `ATTACK_SHAPES`；
- 修正表只允许「登记 → 实测 → 留档」，禁止无数据支撑的批量下调。
