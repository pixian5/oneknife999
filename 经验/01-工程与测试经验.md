# 工程与测试经验

> 来源：`docs/` 各轮开发记录（00–20 分卷、2026-09-30 起各版本进度与专项记录）的提炼。docs 原文不一定正确，以当前代码与实测为准。

## 模块化与纯函数

- 战斗计算（`combat.js`）、掉落（`drops.js`）、技能规则（`skills.js`）、连击/指引（`feedback.js`）、地图几何（`geometry.js`）都应与 DOM 和全局状态解耦，随机数由参数注入，这样 Node 单测可以直接跑，不必启浏览器。
- `main.js` 只做「状态写回 + 视觉反馈」，凡是能写成纯函数的规则都下沉；否则每次小改都要依赖 Playwright 才能验证。
- 新增纯逻辑模块时，语法检查由 `tools/check-syntax.mjs` 自动扫描，不再手工维护 `node --check` 清单；新目录必须落在它的扫描 glob 内。

## 渲染与性能

- HUD 按需渲染（脏检查 + 签名缓存）是帧率的主要来源；`docs/20-界面性能与倒计时修复记录.md` 记录过「每帧重建 DOM」和「倒计时读固定值」两类事故。
- 静态地图用离屏 Canvas 缓存；每帧只重绘动态层。
- `npm run perf` 观察 p95/p99 与 20ms+ 长帧数量。**启动首帧偶发 200ms+ 属正常**（模块解析与首帧编译），不要当成回归。
- 震屏只做相机平移，不能影响点击命中换算；否则移动端会出现「点了没反应」。
- **Canvas 的绘制顺序就是层级**：世界元素的绘制顺序决定谁盖住谁。信息类 HUD（怪物铭牌的血条 / 名字）必须收口到 `drawWorld` 的最后统一绘制，不能留在 `drawEntity` 里按实体顺序画——否则之后任何粒子、飘字、技能环都会盖住血条（0.4.1 的「血条被遮挡」就是结构性成因）。
- **同一套几何被两处引用时必须抽共享函数**：铭牌的「底边位置」同时决定铭牌绘制与伤害飘字的落点，两处各写一份数字必然分叉（0.4.0 的飘字正好压在血条上）。0.4.1 起统一走 `nameplateTop()` / `floatYAboveNameplate()` / `playerNameplateTop()`，新增特效需要避让时也只引用它。
- **视野裁剪要在「建对象」之前做**：铭牌每帧只收集与视口相交的实体（`plateVisible`），排序条目用 `{ y, entity }` 而不是 `{ y, draw: () => ... }`。0.4.1 的写法每帧为全部实体建闭包并排序，0.4.2 去掉后在大地图上省掉一次 filter + map + 闭包分配。
- 飘字这类带速度的世界文字要在绘制时夹进视口（`drawText` 内缩 `size`），否则 `vy: -26` 会让靠地图边缘的 `999` 大字在 1 秒内飞出画布被裁掉。

## 测试组合

- 提交前固定跑：`npm run verify`（check + Prettier + 单测）→ `test:ui`（三视口）→ `test:ui:levelup` → `test:ui:regression` → `test:ui:nameplate` → `perf` → `ONEKNIFE_RUNS=1 npm run test:e2e`。
- **一次性排查脚本要固化成常驻用例**：0.4.1 用插桩脚本定位铭牌遮挡后脚本即弃，问题复发没有回归网；0.4.2 把它写成 `tests/ui-nameplate.cjs`（并入 CI）：加载前插桩主画布的 `fillText` / `fillRect` / `arc` / `roundRect` 与 save/restore 层级，按 rAF 分帧记录绘制顺序，再对「铭牌矩形 × 铭牌之后绘制的世界内容」做相交检测。关键是**用例自带自检**（喂一段只有铭牌内容的日志必须 0 命中，喂人造粒子 / 特效环 / 飘字必须 ≥1 命中），否则插桩失效时会「空跑通过」。
- 插桩只在 `context.canvas.id === "gameCanvas"` 上记录，并把 save/restore 之后（世界块结束）的屏幕坐标 HUD 排除掉，否则连击数字会与铭牌坐标系混在一起产生假阳性；测试中不要用鼠标点击怪物（hover 出的 tooltip 会压住铭牌，是既有设计而非遮挡 bug），接近与出手全部走键盘。
- **远程容器里的 perf 绝对值不可与 macOS 本机对比**：同一份代码在 macOS Chrome 上是 6000+ fps / p99 < 1ms，在容器 headless Chromium（软件渲染）只有 200~240 fps / p99 约 10ms。判定看「p99 与 20ms+ 长帧是否恶化」，不要看平均 fps 的绝对值。
- `tests/e2e-ten-clear-runs.cjs` 用 `fast=1`：玩家伤害 ×25、世界时钟仍是真实时间。**它的死亡数不能直接当作真实难度**（怪物常在前摇期间被击杀），只能当作「流程能否走通」的回归信号。
- 真实难度用 `tests/difficulty-probe.cjs`（`npm run test:difficulty`）：`page.clock` 只快进**虚拟时间**、URL 不带 `fast`，伤害与出手节奏按正式数值结算。**每关必须新建 context + page**，同页连跑会因虚拟时钟 / 自动推进 / 存档写回累积，让第 15 关死亡数从 2 次涨到 17 次。
- 探针的玩家基线要「像正常玩家」：主线等级 + 技能点均分 + 穿戴本关掉落表前 4 件装备 + 带药水。裸装会被首领打进「死亡 → 复活 → 重打首领」的死循环，永远打不完。0.4.2 起同图复活会保留首领已损失生命（`restoreDamagedBoss`，普通怪仍满血），该自放大已大幅缓解，但探针仍应在空闲机器上跑并取中位数。
- 探针判断「半血撤退」必须用游戏侧 `snapshot().player.maxHp`（含装备生命加成），自算 `基础 + 等级×18` 会漏装备加成，撤退阈值形同虚设。
- 远程职业停在射程边缘、近战贴脸；打首领用「一刀一撤」拉开到 `radius + 70` 之外（首领约 104px）。横移 240ms 不够，必须后撤约 320ms。
- 慢脚本给每个目标设预算并定期打印进度（`PROBE FIGHT ... guard / hp / deaths`），否则卡死时看不到任何信号。
- **探针要跑多次取中位数，单次结果会自放大**：同一份代码第 15 关测出过 0 / 1 / 5 死（0.3.6~0.3.8），差异来自「喝药晚一次 → 死亡 → 复活后首领满血重置」的连锁。0.3.9 起每关默认 `ONEKNIFE_PROBE_RUNS=3` 取死亡数与耗时中位数，单次超限只打 `PROBE WARN`、中位数超限才失败——否则一次操作失误就会被误判成「数值回退」。
- **探针要在空闲机器上单独跑**：同一份代码在并行跑 prettier / verify / 其它浏览器任务时，第 15 关测出过 2 死 / 97s 与 16 死以上的连锁（虚拟时钟推进快于实际帧，战斗进程落后）；单独跑同一构建为 0 死 / 57s。结论：探针结果不稳定的第一嫌疑是环境负载，其次是操作模型，最后才是数值。
- 探针喝药阈值要留余量：55% 时一次连击就来不及，改成 65% 后第 15 关三次均 0 死（52 / 53 / 36s），离散度 ±17s。阈值过低会把「操作模型」的问题记到关卡难度上。
- **HUD 数值必须与结算公式同源，不能另写一套近似公式**：角色面板的攻击显示用 `hero.attack + level×4 + 装备有效战力×0.9`（与 `computeDamage` 的 `base` 一致），防御用 `playerDefense()`、生命用 `playerMaxHp()`。如果面板自己算一套（例如把装备战力直接相加、防御乘个系数当「战力」），玩家看到的数字和实际战斗不一致，改数值时也无法靠面板验证。
- **按需渲染的签名必须覆盖所有被展示的值**：`renderPlayer` 用 `panelChanged($("powerText"), signature)` 做脏检查，签名里只放「战力」时，只改防御 / 生命词缀（战力可能不变）会出现面板不刷新的 bug。新增展示项时第一件事是把它加进签名。
- **派生展示的签名要带上它的全部输入**：0.4.0 的装备 tooltip 显示「本件贡献」、背包 tooltip 显示「装备后旧→新」，前者依赖词缀（重铸后变）、后者依赖同部位已穿戴装备（换装后变）。`renderEquipment` / `renderInventory` 的签名分别漏了这两类输入，导致重铸后标题停在旧数值——展示派生值时要顺着依赖链把输入都列进签名，而不是只列主键。
- `__ONEKNIFE_E2E__.snapshot()` 的字段是测试的唯一事实源，脚本按什么算就要有什么：0.3.6 补了 `player.maxHp`，0.3.7 补了敌人 `maxHp`（此前打印 `hp=152/NaN`）。新增测试断言前先确认快照字段齐全，别在测试里自算游戏内数值。
- `balance-sim.mjs` 是无快进数值模拟器，**不复现前摇 / 围攻上限 / 走位躲避**；改了承伤节奏时它不会变，必须用专项 Playwright 复现（如沙蝎王战连跑 3 次）。
- 临时复现脚本（Playwright）不入库，验证完删除；仓库只保留 `tests/` 下的常驻用例。

## 交互与面板

- 面板形态要服从既有 e2e 约束：百图回归依赖 `page.mouse.click(canvas)` 寻路且每个动作后按 `f`，所以**城镇商店做成侧栏面板而不是全屏遮罩**（遮罩会吞点击、F 会反复弹遮罩）。要改造成模态弹窗，必须先跑百图回归。
- 复用已有按键（如 `F`）扩展交互时，优先级必须显式：掉落 > 秘藏 / 场景节点 > 城镇 NPC。新增 NPC 要接着往后排，否则会出现「按 F 开了面板却拾不到东西」。
- 瞬态 UI 状态（`state.shopOpen`）不写存档，并且在换图 / 复活 / 条件失效（走出城镇）时统一复位，避免跨场景残留。
- 新增玩家字段（如 `reforgeScroll`）优先给默认值而不是升存档版本：`loadGame` 里缺省兜底即可，迁移表只用于结构变化。
- 写「注入存档」类浏览器测试时注意 `persistGame` 同时写顶层 `equipment` 与 `player.equipment`，而 `loadGame` 优先读顶层；两处都要改，否则穿戴装备不会恢复。
- 专项 UI 测试要确认玩家真的站在触发区域：`ash_outskirts` 的城镇是 y 950~1250，出生点 y 780，进城需要先向下走约 1 秒。

## 常见坑

- 遍历 `state.entities` 的新逻辑必须跳过 `friendly`（骨卫）与 `npc`（流浪武者），否则会把召唤物当怪打、把 NPC 拉进自动索敌。
- e2e 快照也要过滤 `friendly`，不然断言里的实体数量会随召唤波动。
- 存档迁移用「版本函数表」逐级升级（v2→v3→v4），不要写一次性大 if；拒绝读取更高版本存档。
- 用系统 Chrome 做 Playwright 测试（`tests/browser-options.cjs`），避免在 macOS 上反复下载浏览器。
- **下载一律优先走镜像源**：云电脑里直连 Playwright CDN（`cdn.playwright.dev`）实测只有 50~150 KB/s，186MB 的 Chromium 要 30 分钟以上，并行分段也提不上去；换成 npmmirror 后同一文件 **138MB / 12 秒**。浏览器包地址：`https://registry.npmmirror.com/-/binary/chrome-for-testing/<版本>/linux64/chrome-linux64.zip`；npm 依赖用 `--registry=https://registry.npmmirror.com`。若 Playwright 自己的 `install` 卡在 0%，直接镜像下 zip → 解压到 `~/.cache/ms-playwright/chromium-<rev>/chrome-linux64/` → `touch INSTALLATION_COMPLETE`，再用 `npx playwright install-deps chromium` 补系统库（缺 `libatk-1.0.so.0` 就是这一步没跑）。无头模式还会单独找 `chromium_headless_shell-<rev>/chrome-headless-shell-linux64/`，必须同一个镜像下载 `chrome-headless-shell-linux64.zip`，否则报「Executable doesn't exist」。

## 0.8.x 增补（2026-11，GLM 补记）

- **测试双轨开关**：改变核心节奏的功能（行为系统 `noabilities`、施法前摇 `fastcast`）一律做成 e2e URL 参数开关——真实玩家恒开、e2e 默认关（探针与全部既有回归节奏零影响）、`&realcast=1` 测真实链路。没有这层，一次手感改动会让全难度闸门数据失效。
- **CI matrix 会落后于测试资产**：新增 `test:ui:*` 必须同步进 `.github/workflows/ci.yml` 的 matrix（0.8.36 时 matrix 只有 7/14，abyss/cast 等仅本地跑）。perf 进 CI 用 `ONEKNIFE_PERF_P99_MAX=12`（Ubuntu 软件渲染与 macOS 不可比），零 20ms+ 长帧仍是硬指标。
- **多段补丁脚本必须每段落盘**：python 批量改代码时把 `write` 放最后是反复踩的坑（0.8.27、0.8.35 两次）——中途断言失败会让已成功的替换静默丢失。正确姿势：每段替换后立即 write，或分段独立执行。
- **loadGame 的 catch 会吞渲染层异常**：症状是「读档失效回职业选择」，真因常是 render 层新代码抛 ReferenceError。0.8.7 起有内部日志系统（logger.js），console 未必有输出——排查先看 logWarn/logError 落点。
- **Service Worker 版本三处同步**（0.8.36 PWA）：`VERSION`、`sw.js` 的 CACHE_VERSION、`main.js` 的 CURRENT_APP_VERSION 必须一起改，`scripts/deploy-hf.py` 有校验拦截。素材绝不全量预缓存（108MB 会爆配额），壳 + 按需缓存 + 导航网络优先。**实际到 0.8.75 才发现 `main.js` 的 CURRENT_APP_VERSION 仍停在 0.8.56**：版本号只改两处、部署脚本没跑就会一直漏；每轮升版后直接跑一次 `python3 scripts/deploy-hf.py` 的版本校验（或完整 dry-run），不要只信 `check`。
- **本机 VM 没有 Google Chrome**：`tests/browser-options.cjs` 默认 `channel: "chrome"` 会报 `/opt/google/chrome/chrome` 不存在；系统 `chromium` 在 `/usr/local/bin/chromium`，所有浏览器回归前加 `ONEKNIFE_CHROMIUM_PATH=/usr/local/bin/chromium`。别为此下载 Chrome，也不要改默认 channel 污染 macOS。
- **断点续跑的并发隔离**（0.8.21）：多职业并发跑 e2e 时 checkpoint 文件名必须按轮次分文件，否则互相覆盖。
- **动手前先实证素材现状**（0.8.35 两次教训）：待办清单会撒谎——「20 张黑底图」早已透明化、「深层专属怪池」12 物种 0.6.0 已全进章表。先跑 PIL 四角 alpha / 目录 diff 实证，再定方案。
- **贴图替换几何必须显式跳过旧几何**（0.8.29）：「画了但看不见」的真相是叠加渲染被旧几何遮挡（prop 贴图边缘透明、主体居中被三角盖住）。特效类才用叠加语义。

## 全量覆盖与 fast 模式（0.8.42）

- **`fast=1` 只放大玩家伤害（×25）并把首领单次受击封到 18% 最大生命**，怪物伤害、关卡、AI、掉落、贴图加载都不变。它能证明「100 关能通、内存稳、资源齐」，但会把首领战压到 6–14 秒，**不能用来判断手感与难度**：实测 fast 首领占比 35%–41%，真实速度 1–39 关是 73.5%。
- **真实手感的样本要单独跑**，且要标清口径；不要拿 fast 的全量时长做章节节奏曲线。
- **资源 404 只在深层暴露**：装备图标 `equip-ringL/ringR/braceletL/braceletR.png` 在前期没有对应掉落，跑到 40 关后才出现；短程冒烟（10 关）404 为 0，不能证明资源齐。
- **同类路径拼接要收口到一个函数**：装备面板、商店、重铸、背包各写一遍 `equip-${slot}`，就是 404 的来源；抽 `equipIconKey` 后加源码契约测试，禁止裸 slot。
- **内存预算要看「触顶后是否回落」**：贴图从 12MB 涨到 128MB 触顶、LRU 淘汰后稳定在 120–128MB，跑完 100 关不涨，才算治理成立；只看单关数字不够。

## 0.8.67 真实键鼠试玩也会被“工具策略”污染
- `tools/run_abyss.py` 首领阶段只锁定 boss，不打首领召唤的增援；而游戏 HUD 明确写“首领附近还有 X 只小怪，先清小怪或用范围技能再打首领”。
- F70 实测 19 次死亡里 16 次死于帝陵增援（镇国妖师 8、苔冠树精 4、藤蔓缚妖 3、玉髓守卫 1），只有 2 次首领本体、1 次地面危险区；330.2 秒里大量时间花在死亡后走回与重打。
- 真实键鼠事件只保证输入真实，不保证策略像人。做难度结论前必须检查 `diagnostics.deaths` 的 killer 分布，并把工具策略与游戏数值分开写。
- 0.8.68 的 A/B 直接否定了“先清增援”：F71 清增援 185.9s/+9，只打 boss 122.1s/+5；F72 清增援 192.9s/+11，只打 boss 179.1s/+9。自动脚本切目标要重新走位、点击，追着单只增援点杀会被“清一只、召一只”拖死；`combo` 的 4/3/2/1 范围技能在锁 boss 时本来就会扫到近身增援。
- 结论：**“真人会先清增援”不等于“脚本追着单只增援更优”**。工具策略的改动必须先做同层 A/B，不能凭 HUD 文案或直觉直接写成“正确修法”。清增援代码已回退，只保留只锁 boss 的版本。

## 0.8.68 run_abyss 单实例锁
- 同时跑两个 `run_abyss` 会互抢同一页面的键鼠事件：日志重复、目标来回切、层数据失真。`kill` 外层 shell 也不等于杀掉子进程。
- 正确做法是进程内锁：`saves/.run_abyss.lock` 写 PID，启动时用 `os.kill(pid, 0)` 判断旧进程是否存活，存活就拒绝启动；`atexit` 只删自己持有的锁。
- 锁文件是运行时产物，必须写进 `.gitignore`；测试时要实际启动第二个进程，确认报“已有 run_abyss 在运行”而不是只做静态检查。
- 另一个更隐蔽的遗漏：`run_abyss` 的完成 JSON 一直 `resourceClaimed:false`，说明它从不按 F 开补给箱。只看“清层成功”会漏掉“补给链路未走”，死亡与用时都会被放大。

## 0.8.69 只读快照暴露战术点，工具才能真正“按 F 开箱”

## 统计口径与脚本退出码（0.8.43）

- **退出码要在失败路径上非零**：`for` 循环跑满自然结束会返回 `0`，长跑脚本必须显式 `exit 1`，否则调用方把「重试耗尽」当成功。判定成功要同时看产物（存档 `completed`）与退出码，不能只看其一。
- **统计字段先问「它度量什么」**：`期初库存 − 期末库存` 是净变化不是使用次数，喝一瓶又拾一瓶会记 0、补给更多会为负；正确做法是在真正扣药的唯一入口累加计数（`main.js` 的 `potionsUsed`），把库存变化另存一个字段。
- **结算快照不等于战斗开始时的值**：想记「首领最大生命」必须在开战时取，击杀后 `alive` 过滤会把它变成 `0`。凡「XXX 最大值 / 初始值」类字段，都在状态还存在时采集。
- **缺测不要用哨兵值参与算术**：`-1 − (−1) = 0` 会把「没读到」伪装成「零增长」。读不到就返回 `null` 并打印「未测得」，宁可少一个数字也不给假结论。
- **长跑要能续**：分段脚本按段落盘（`seg-N.json` + `save-N.json`），中断后可从已有段复用继续，不必从头重跑；包装进程自身被信号杀掉时，子进程要用独立进程组才能一起收掉。


## 0.8.77 长期分叉合并与 Git 历史清理
- **先确认每条线的 upstream，再比较分支**：本地 `main` 可能只是过期副本（0.8.39，ahead 1 / behind 21），不能拿它当远端 `main`；`work` 的 upstream 还可能错指 `gitcode/main`。比较前先 `git fetch --all --prune`、`git branch -vv`，以远端 ref 为准。
- **长分叉优先把“外围线”并进“主线”**：`main` 的价值是可搬运的资产/工具/统计修复，`work` 是当前玩法主线；`main → work --no-ff` 冲突少，还能保留汇合点。不要为了“看起来线性”去 rebase 已推送的 49 个提交。
- **冲突解决不能只按“取一边”**：自动合并进来的脚本可能依赖被丢弃侧的字段。0.8.77 的 `tools/playthrough.cjs` 已读 `snap.player.potionsUsed`，若 `main.js` 只取 `work` 版，`potionUsed` 会静默变成 `NaN`。解法是先列出对侧新增的消费点，再逐项回填并跑对应测试。
- **历史垃圾先按对象测量，不信提交说明**：`main` 写“约 100MB”，实测三组只有约 11.2MiB。用 `git rev-list --objects --all | git cat-file --batch-check` 按路径汇总对象数与字节，别按目录名猜。
- **改写历史前必须 `git bundle --all`**：`filter-branch` 后旧 SHA 全部失效，bundle 是唯一完整回滚入口；清理后 `rm -rf refs/original`、`git reflog expire --expire=now --all`、`git gc --prune=now`，再强推。
- **只删远端分支不够，旧对象仍可能被引用**：过期的 `deploy/0.8.6` / `trae/agent-SYLj24` 指向旧线，强推 `work/main` 后要一并删除，否则旧垃圾仍可从这些 ref 到达。
- **状态类回归要同时匹配“状态 + 命中者”**：只等 `slowTimer > 0` 会在上一场残留计时或旧 `lastKiller` 上假阳性。0.8.77 改成 `waitForStatus` 同时要求 `lastKiller === 本次目标名`，并让 `loadMap` 清空 `lastKiller`；这样测试停止点一定是本场真实命中。
- **历史改写后的协作成本要写进 README**：其他克隆不能 `git pull`，必须 `fetch --all --prune` + `reset --hard origin/work`；公共部署（Instabox）跟 `main` 时，还要把 `main` 快进到合并结果才会显示新版本。

## 工程门禁与素材体积（0.8.78）
- **版本号有五个副本**：`VERSION`、`package.json`、`package-lock.json`（两处）、`CURRENT_APP_VERSION`、`sw.js` 的 `CACHE_VERSION`。只改前三个会让 PWA 继续吃旧缓存；`tools/check-version.mjs` 一次校验，提交前必跑。
- **SW `SHELL` 清单也要门禁**：新增 ES 模块忘加 `SHELL`，在线正常、离线白屏；`check-version` 同时校验清单覆盖 `game/src/*.js` 且不含不存在文件。
- **素材预算要分类型**：地图底图 1600×900 放宽到 450KB，非地图单图 500KB，总量 60MB；只设总量会让单张 2MB 的分隔图混过去。`tools/asset-budget.mjs` 同时禁止 0 字节文件。
- **素材审计的失败路径必须非零退出**：只打印“缺失 N 帧”会让 CI 绿着放行；`asset-audit` 对缺帧/完全无自有素材 `exit 1`，只静态原画保留提示。
- **压缩按实际显示尺寸做，不按原图尺寸做**：怪物 160×160 用 128 色调色板够用，技能图标缩到 128 后再压 128 色；玩家/装备缩到 256 再压。先缩尺寸再降色，比只降色省得多。
- **压缩后必须全量解码 + 实拍**：`identify` 只能证明文件可读，不能证明透明边缘、色阶和暗部没有坏；0.8.78 用桌面/移动/360/320 截图与 `status-real` 六例复核。调色板是有损的，原图永远留在 `art-source/` 或 tar 备份，不拿压缩件当美术源。
- **旧素材先移出运行目录，再压缩**：55 个旧 `monster-*.png` 约 41.3MB，运行时根本不再引用；先移到 `art-source/monster-legacy/` 并 gitignore，资产从 114MB 直接降到约 72MB，本批压到 29.3MB；合并美术线 46 只独立四帧后又回到 35.6MB/940，仍低于 60MB。顺序反了会把时间浪费在压缩死文件上。
- **别名优先级要按“是否有自有帧”判断**：`resolveMonsterSpriteName` 必须先查自身白名单，再回退别名；只按别名表优先会让新增独立原画的怪继续借别人的帧（第 7 关 `loadedFrames=[]`）。`asset-audit` 的 `aliasReusedNames` 也要用 `ownFrames === 0` 过滤，否则审计数会虚高。
- **派生四帧不是真实动作原画**：46 只怪用静态图派生 160×160 RGBA 四帧，`idle` 归一化、`walk/attack/hit` 小幅旋转位移，属于程序化占位；能解决“借别人帧”，不能解决“动作僵硬”。真实逐帧原画到位后直接覆盖同名文件，不要重复生成派生帧。
- **离线压缩工具要和运行时解耦**：本次用 ImageMagick 手工批处理，`tools/optimize-assets.mjs` 仍是旧的 sharp 工具，不在 `verify` 路径；不要把一次性压缩脚本伪装成常驻构建步骤。
